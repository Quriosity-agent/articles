# Fable 5 vs GPT-5.6 Sol：真正的问题不是谁更聪明，而是谁更适合交付

> **TL;DR:** Peter Gostev 在 X 上把 Fable 5 和 GPT-5.6 Sol 的差异概括成一种很实用的体感：Fable 5 更像高洞察、高表达、适合讨论和写作的模型；GPT-5.6 Sol 更像长期执行、少漏项、能把任务做完的工作模型。这条帖子的价值不在于给出严格排名，而在于提醒团队：前沿模型正在分化成不同的工作角色。选模型不能只问“谁更强”，还要问“这个任务需要判断、表达、执行、验收，还是长时间不掉线”。

## 一句话判断

**这条帖子的核心不是“Fable 5 和 GPT-5.6 Sol 谁赢”，而是“同一代前沿模型开始像不同类型的同事”。**

Peter Gostev 的原帖开头就强调：这不是严格 benchmark，而是他的使用体感。他认为 Fable 5 在“纯智能”、洞察和表达上更强；GPT-5.6 Sol 则在可靠执行、任务完成、少漏项和长时间工作上更让人放心。

这和过去一年很多模型比较的语气不太一样。过去的讨论常常追求一个总榜：谁的 Elo 更高、谁的 SWE-bench 更高、谁的数学更强。Gostev 这条帖子的有用之处在于，它把模型选择从“冠军心态”拉回到工作流心态：

| 任务类型 | 更像 Fable 5 的位置 | 更像 GPT-5.6 Sol 的位置 |
|---|---|---|
| 早期架构讨论 | 提出判断、权衡、表达方案 | 拆解可执行任务和验证路径 |
| UI / App 从零构思 | 设计感、流程感、初稿质量 | 补齐细节、减少漏项、按既有模式实现 |
| 写作和沟通 | 语言更自然、论述更清楚 | 可用，但需要更多校准 |
| 复杂实现 | 可能给出聪明方案，但需严查落地 | 更适合长时间执行和验收 |
| 多步骤任务 | 适合方向判断 | 适合清单式推进、工具调用、子任务管理 |
| 长程 agent | 适合高层计划 | 适合持续跑、持续修、持续交付 |

这个分法不是客观真理，但它很接近团队真实用模型时会遇到的问题：不是每个任务都需要“最会说话”的模型，也不是每个任务都适合交给“最会干活”的模型。

## 原帖真正抓住的是“能力形状”

Gostev 对 GPT-5.6 Sol 的赞赏集中在几个词：diligent、robustness、reliability、computer use、sub agents、adhering to existing code patterns、multi-day runs、token efficiency。

翻译成产品语言，就是：

1. **能不能把清单做完**：给它 8 件事，是否真的逐项完成；
2. **能不能少漏关键细节**：不是每一步都惊艳，而是不频繁遗漏必要步骤；
3. **能不能贴合现有代码风格**：不是重写一套“模型觉得更好”的架构，而是进入现有系统；
4. **能不能长时间推进**：几个小时甚至几天的任务，是否还保持目标和上下文；
5. **能不能管理工具和子任务**：不只是回答，而是调度浏览器、代码、文件、子线程和检查步骤。

这些能力听起来没有“推理智商”性感，但在 agent 产品里非常贵。

真实工作里的失败，往往不是模型完全不会，而是它差一点：少改一个文件、忘记跑测试、没有更新索引、把既有风格打乱、写了一个听起来对但没验证的 benchmark。Gostev 提到他让两个模型做新 benchmark：GPT-5.6 Sol 花了 6 小时到 2 天，做出经过测试、能工作的版本；Fable 5 更快返回，但结果更像由模型自评通过的“感觉正确”。这只是个体经验，不该当成普遍结论；但它指出了一个真实风险：**聪明的草案不等于可交付的系统。**

## Fable 5 的优势也不能被低估

另一边，Gostev 并没有说 Fable 5 弱。他的判断反而是：Fable 5 在“纯智能”上更强，低 reasoning 下也更有洞察，写作和解释更好，从零做 UI 的 flow 也可能更舒服。

Anthropic 官方对 Fable 5 的定位也支持这种“高判断、高表达、高复杂任务能力”的方向。Anthropic 在发布页中把 Fable 5 和 Mythos 5 放在第五代 Claude 模型里，强调它们能比之前的 Claude 模型更长时间自主工作，并提到软件工程、知识工作、视觉、记忆和生命科学等能力。官方还特别提到 Fable 5 在视觉任务、长上下文、代码迁移和复杂分析中的表现。

所以如果任务处在“还不知道怎么想”的阶段，Fable 5 很可能是更好的第一站：

- 帮你拆问题；
- 提出不同架构路线；
- 解释复杂 trade-off；
- 写面向人的文档、PRD、叙事、邮件；
- 给一个产品或研究方向做高层判断。

这类任务的成功标准不是“有没有把 8 个 checkbox 都勾上”，而是“有没有形成更好的问题理解”。这正是许多执行型模型容易显得笨拙的地方：它们会很快进入任务模式，却未必先把问题重新组织清楚。

## GPT-5.6 Sol 的优势是“交付闭环”

OpenAI 对 GPT-5.6 Sol 的官方叙述也很明确：更高 token 效率、更强 coding、knowledge work、computer use、tool coordination，以及 `max` reasoning 和 `ultra` 多 agent 模式。OpenAI 在 2026 年 7 月 9 日的正式发布页里说，GPT-5.6 家族包括 Sol、Terra、Luna；Sol 是旗舰模型，`ultra` 通过多 agent 并行处理复杂任务。预览页还把 Terminal-Bench 2.1 描述为测试 planning、iteration 和 tool coordination 的命令行工作流。

这些点和 Gostev 的体感高度一致。他特别喜欢 GPT-5.6 Sol 的地方，几乎都围绕“交付闭环”：

- 视频剪辑开始可用：长素材能产出短 highlight；
- computer use 变得实用；
- 子 agent 和多线程管理更流畅；
- 自动贴合现有代码模式；
- 研究更可引导；
- `/goal` 这类多日运行开始有意义；
- 比 GPT-5.5 更省 token、更快，实际使用里也更快于 Fable。

这里最关键的是“闭环”。一个 agent 不只是给答案，它要观察环境、行动、读反馈、修正、继续行动，最后交付可验证结果。只要中间有一步松掉，结果就会变成“看起来完成了”。

GPT-5.6 Sol 的产品价值，如果 Gostev 的体感能代表一部分真实使用，就是它降低了这种松掉的概率。

## 最好的用法不是二选一，而是路由

Gostev 最后给的建议很朴素：如果可以，两个都用，并逐步找到各自适合的任务。他举的组合是：用 Fable 做架构讨论，用 GPT-5.6 Sol 做实现，用 Fable 做文档和沟通。

我觉得这正是下一阶段模型使用的主线：**不是选一个万能模型，而是建立模型路由。**

一个比较稳的工作流可以长这样：

| 阶段 | 主要问题 | 推荐角色 |
|---|---|---|
| 0. 问题澄清 | 这个任务真正要解决什么？边界是什么？ | Fable 5 |
| 1. 架构/方案 | 有哪些路线？各自风险是什么？ | Fable 5 + GPT-5.6 Sol 交叉审查 |
| 2. 实施计划 | 要改哪些文件？验收条件是什么？ | GPT-5.6 Sol |
| 3. 执行 | 写代码、跑命令、修错误、更新索引 | GPT-5.6 Sol |
| 4. 复核 | 有没有过度实现、漏项、论证不清？ | Fable 5 |
| 5. 发布 | 测试、提交、推送、变更说明 | GPT-5.6 Sol |
| 6. 对外表达 | 写文章、说明、PRD、发布稿 | Fable 5，必要时 GPT-5.6 Sol 校验事实 |

这不是“某模型永远做某事”，而是用任务阶段来分配认知风格。前期需要发散和判断，后期需要执行和闭环。一个模型负责所有阶段，当然方便；但当任务真的值钱时，路由往往更稳。

## 这也改变了我们该怎么评测模型

Gostev 这条帖子的另一个隐含观点是：标准 benchmark 不足以解释真实体感。

两个模型可能在总榜上接近，但使用起来完全不同。原因是很多关键差异不在最终分数，而在失败模式：

- 会不会漏掉用户明确列出的事项；
- 会不会不看现有代码模式就重构；
- 会不会在第 7 步忘记第 2 步的约束；
- 会不会把自评当验收；
- 会不会在工具失败后继续装作完成；
- 会不会写得漂亮但无法运行；
- 会不会遇到局部循环后自己跳出来。

所以团队内部更应该做“工作流评测”，而不是只看模型榜单。比如：

1. 给同一个真实任务，要求模型从 issue 到 PR 完成；
2. 记录遗漏项、测试次数、返工次数、人工介入次数；
3. 分开评估方案质量、实现质量、代码风格一致性、验收完整性；
4. 看 3 小时、8 小时、24 小时任务中的目标保持能力；
5. 用人类 reviewer 判断：这次输出是“聪明”，还是“可合并”。

这样才能解释为什么一个模型让你觉得“更聪明”，另一个模型却让你更愿意把脏活交给它。

## 使用建议：给模型写不同的任务合同

如果团队同时使用 Fable 5 和 GPT-5.6 Sol，我会把 prompt 和验收方式也分开。

给 Fable 5 的任务，可以更像思考合同：

- “先给我三种方案和你最担心的失败点。”
- “不要急着实现，先审视这个需求是否值得做。”
- “把这个设计解释给产品、工程和运营三类人。”
- “找出这篇文章里最薄弱的论证。”

给 GPT-5.6 Sol 的任务，要更像交付合同：

- “按清单完成，每完成一项就验证一次。”
- “优先沿用现有代码模式，不要引入新框架。”
- “修改后运行这些测试，并把失败原因修掉。”
- “如果发现需求不清，先给出最小可执行假设，然后继续。”
- “最后列出改了哪些文件、怎么验证、还有什么风险。”

这类分工比“哪个模型更好”更有价值。模型越强，越需要明确它在工作系统里的职责。

## Caveats：这条帖不是严谨实验

需要把边界说清楚。

第一，Gostev 的原帖是个人体感，不是受控实验。它没有公开完整 prompt、任务集、采样参数、上下文长度、失败判定和人工介入边界。

第二，Fable 5 和 GPT-5.6 Sol 都处在新近发布和快速迭代阶段。2026 年 7 月 10 日看见的能力、价格、产品入口和限额，之后都可能变化。

第三，不同用户会给出很不同的结论。写作风格、代码库类型、任务复杂度、是否会写验收条件、是否让模型用工具，都会显著改变体感。

第四，OpenAI 和 Anthropic 官方页面里的 benchmark 也有各自的选择和产品叙事。它们适合作为背景，不应直接替代你自己的任务评测。

所以这篇文章的结论不是“Fable 5 输给 GPT-5.6 Sol”，也不是“GPT-5.6 Sol 不够聪明”。更准确的结论是：**前沿模型正在形成不同的能力形状，团队需要从模型崇拜转向模型编排。**

## 结论

Peter Gostev 这条 X 值得写，是因为它把一个很多人已经隐约感受到的变化说清楚了：

**模型不再只是同一把尺子上的高低差，而是在不同工作环节里呈现出不同性格。**

Fable 5 可能更适合高层判断、写作、架构讨论和概念整理。GPT-5.6 Sol 可能更适合执行、代码修改、工具调用、长程任务和最终交付。真正成熟的团队不会只问“谁更强”，而会问：

- 这个阶段需要洞察还是完成？
- 需要表达还是验收？
- 需要发散还是收敛？
- 需要一次好答案，还是 200 次小动作都别掉链子？

这也是 agent 时代最实用的模型观：把模型当成工作流里的角色，而不是排行榜上的名字。
