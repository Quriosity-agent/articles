# reelbench-skills Deep Dive: Reliable AI Shot Analysis Separates Measurement, Judgment, and Validation

> **TL;DR:** reelbench-skills is neither a video-generation model nor a prompt that asks a multimodal model to improvise an entire shot analysis. It contains two Skills for Claude Code and Codex. `video-shots` uses ffprobe, FFmpeg, and frame differences to measure cuts, durations, and motion evidence; the model fills only semantic fields such as shot size, category, camera behavior, visual description, and rhythm; 15 deterministic quality gates then validate the result. `video-sync` turns the source footage and shot table into a video whose analysis panel scrolls and highlights at every cut. The transferable idea is not “one command.” It is keeping facts, judgments, and acceptance checks separate.

## The short answer

The most accurate description of reelbench-skills is: **an agentic shot-analysis toolchain that connects media measurement, model annotation, rule-based validation, and visual delivery.**

It overlaps with the previously covered [Lapian Notes local film-analysis workbench](../2026-07-09/2026-07-09-lapian-notes-ai-film-analysis-workbench-en.md), but its center of gravity is different. Lapian Notes is primarily an interactive place for a person to watch, inspect, and record observations. reelbench-skills emphasizes an executable pipeline: which fields come from machines, which fields a model may judge, what errors code must reject, and how the resulting data becomes an annotated video.

The repository currently contains two Skills:

| Skill | Input | Main outputs | Problem solved |
|---|---|---|---|
| `video-shots` | Source video | `shots.json`, `track.json`, keyframes, Markdown, interactive HTML | Converts a finished video into inspectable, reusable shot data |
| `video-sync` | Source video, `shots.json`, keyframes | MP4 with a synchronized analysis panel | Turns analysis into a teaching, review, or publishing artifact |

It is therefore not a programmatic video engine like Remotion. Remotion answers how code becomes video. reelbench-skills answers how an existing video becomes an evidence-backed, testable shot analysis, with FFmpeg still performing the actual media processing and composition.

## The central design: machines measure, models judge, code checks

The README summarizes the engineering boundary succinctly: FFmpeg measures cuts and durations, the model decides only what requires judgment, and quality gates reconcile the result.

Those are three different data responsibilities:

| Layer | Responsibility | Typical fields | Reason for separation |
|---|---|---|---|
| Machine measurement | Facts directly computable from media | Duration, dimensions, frame rate, cut times, per-shot start/end/seconds, motion curve | Prevents the model from inventing timeline values |
| Model annotation | Information requiring visual semantics | Shot size, category, camera behavior, frame description, subjects, subtitles, sound, rhythm | Keeps the model focused on recognition and interpretation |
| Code validation | Whether the result is internally consistent and evidenced | Legal enums, continuous timeline, keyframe presence, cast reconciliation, motion consistency | Converts “looks finished” into executable pass or failure |

This separation matters more than swapping in a larger vision model. The most damaging shot-analysis errors are often not awkward prose. They are shifted boundaries, inconsistent durations, missing shot numbers, major camera movement attached to a static signal, or complete-looking columns with no supporting evidence. A model can produce fluent text, but it should not be the sole source for machine-verifiable facts.

## How `video-shots` actually runs

`video-shots` is a pipeline with durable intermediate artifacts, not one model call:

1. `seed` reads metadata through ffprobe, generates candidate cuts with FFmpeg scene detection, and computes a frame-level motion track.
2. `frames` extracts two frames around 15% and 85% of every shot, producing paired evidence such as `S01a` and `S01b`.
3. `sheet` arranges those frames as contact sheets so the model can compare the beginning and end of each shot.
4. The agent fills semantic fields in batches. The Skill recommends no more than 25 shots per batch to reduce omissions and cross-shot contamination.
5. When scene detection misses or invents a cut, `recut --split` and `--merge` change only valid boundaries, then renumber shots, recalculate time, and record the decision in `manualCuts`.
6. `validate` runs 15 quality gates and exits nonzero on blocking errors.
7. `render` writes a Markdown table and a single-file interactive HTML report.

The default scene threshold is 0.3, but it is not a universal constant. Dark or slowly edited material may need a value around 0.15, while fast cutting may justify a higher threshold. Dissolves can be missed; flashes, handheld motion, and fast subjects can produce false cuts. Automatic detection is therefore treated as initial evidence rather than an immutable answer.

## A motion curve is evidence, not a camera-motion classifier

By default, the project samples at roughly 5 Hz, resizes frames to 64×36, computes mean adjacent-frame pixel differences, and uses the median inside each shot to reduce spikes at cut boundaries. This is cheap and stable evidence for whether the image changed substantially.

It cannot distinguish among:

- a push, pull, pan, tilt, or tracking move;
- movement by people or objects;
- changes in light, effects, or exposure;
- handheld movement affecting the whole frame.

The camera-motion gate is intentionally asymmetric. If the model claims a major push or tracking move while measured motion is nearly zero, the gate can reject it. If the model says the camera is locked while motion is high, the system emits a warning because the subject, rather than the camera, may be moving.

That restraint is one of the project's better decisions. A cheap frame-difference metric is not marketed as “AI camera-motion detection.” Its evidentiary limits are encoded into the validator.

## What the 15 quality gates check

The gates go beyond JSON syntax. They test whether the shot table deserves trust:

| Category | Checks |
|---|---|
| Timeline | Ordered shots, contiguous boundaries, coverage from zero to the end, and `seconds = end - start` |
| Identity and enums | Continuous shot IDs plus legal shot-size, category, camera, and transition values |
| Description quality | Checkable visual descriptions without mass-duplicated template prose |
| Semantic consistency | Subjects reconcile with cast; shot categories have supporting description evidence |
| Machine evidence | Camera claims fit the motion curve; boundaries come from detected or registered manual cuts |
| Asset completeness | Both keyframes exist for every shot |
| Rhythm | Either omit the column entirely or annotate every shot with a legal rhythm label |

One subtle rule matters: **skipped is not passed.** If validation receives no `track.json`, cast data, or frame directory, the relevant gate is marked skipped rather than green. Missing evidence is not silently converted into success.

For this review, the current `video-shots` self-test passed **449 assertions**, and every quality gate has an adversarial case proving that it can fail. The WeChat article cited 436 assertions. That was accurate for an earlier revision, but the number had already changed as the young project evolved.

## The report is an interface, not a screenshot

`shots-report.html` is a single file with no external dependencies and can be opened offline. It includes a local video player, rhythm strip, synchronized current-shot highlighting, click-to-seek navigation, search, filters, sorting, list and card views, paired keyframes, shot-size and camera distributions, cast statistics, quality results, and JSON export.

The video itself is not embedded. The report points to the original path, so a user opening it on another machine must select the local video again. That keeps the page small, but it is not a fully self-contained media archive.

![The responsive mobile report](imgs/reelbench-skills-measured-shot-analysis/02-report-mobile.png)

The official Chinese demo analyzes a 202.9-second AI short as 53 shots: a 3.83-second average shot length and 15.7 cuts per minute. All 15 gates pass, while two non-blocking warnings remain as examples: S46 is labeled locked-off despite relatively high measured motion, and S48 through S53 use the same `close` rhythm label six times in a row.

We re-ran the current validator against that demo and reproduced the documented result. The English demo also passed all 15 gates: 287.37 seconds, 46 shots, a 6.25-second average, and 9.6 cuts per minute. Its unusually long shot remains intact because it is genuinely uncut; scene detection does not manufacture boundaries merely to make the distribution look regular.

## How `video-sync` turns the table back into video

`video-sync` takes the source clip, `shots.json`, and optional keyframes, then produces an MP4 with footage and shot information playing together.

![The video-sync shot-information panel](imgs/reelbench-skills-measured-shot-analysis/03-video-sync-panel.png)

It does not capture a browser screenshot for every output frame. A headless Chrome or Chromium instance first renders three tall panel images: static information, a dim shot list, and a highlighted shot list. FFmpeg then uses cut timestamps with `sendcmd`, crop, and overlay operations to scroll the list and move the highlight.

The active shot is normally anchored near the second row. The panel eases into place over roughly 0.45 seconds, then stays still until the next cut. Landscape footage uses a vertical stack; portrait footage places video and analysis side by side. Original audio is copied with `-c:a copy` rather than re-encoded.

![Portrait footage composed beside its synchronized shot panel](imgs/reelbench-skills-measured-shot-analysis/04-video-sync-output.png)

This “few browser renders plus dynamic FFmpeg crops” design is lighter than rendering a web page per frame and keeps styling centralized in HTML and CSS. The current `video-sync` self-test passed **122 assertions** covering landscape, square, and portrait geometry, even dimensions, scale bounds, scroll anchoring, and command construction. The self-test itself does not launch a browser or FFmpeg.

## Where the “one command” framing needs context

The WeChat headline compresses the experience into one command. That is a useful interface description, not a literal architecture diagram.

A user can ask an agent to analyze a video and let the Skill orchestrate scripts and model work. The install script also symlinks the Skills into `~/.claude/skills/` or `~/.codex/skills/`. The complete process still includes probing, scene detection, frame extraction, batched semantic annotation, optional manual recuts, validation, report rendering, and optional synchronized-video composition.

Dependencies also need precise wording. The project has **zero npm dependencies and requires no separate API key**, but it is not dependency-free. It needs Node.js 18+, FFmpeg, and ffprobe. `video-sync` additionally needs Chrome, Chromium, or Edge to render the panel. Model inference consumes the active Claude Code or Codex session allowance; removing API-key configuration does not remove compute cost.

## What it explicitly does not do

The `video-shots` specification draws clear boundaries:

- no ASR; dialogue comes only from burned-in subtitles, otherwise audio remains blank;
- no face recognition or automatic cross-shot cast merging;
- no qualitative verdict on whether a film is good;
- no editing or exporting individual shot clips;
- no within-shot object detection or tracking.

Three broader limitations remain. First, semantic fields are still written by a model or person. Gates can detect contradictions, but they cannot prove that “medium shot,” “reaction shot,” or “payoff” is the correct interpretation. Second, the bundled demos are author-provided fixtures, not an independent benchmark. Third, the repository was only days old at review time and had no tag or release; interfaces and assertion counts may continue to move quickly.

## Where it becomes useful in an AI-video workflow

Its best use is not a mysterious overall quality score. It is a comparable data layer:

- compare average shot length, cutting rate, and shot-size distribution across generations of the same prompt;
- detect runs of close-ups, long static stretches, or collapsed rhythm labels;
- generate synchronized teaching and review videos for editors, directors, and prompt researchers;
- pass a shot table to later agents instead of repeatedly asking them to watch the entire video;
- preserve measurements separately from aesthetic judgments in batch-generation workflows.

For an editor such as QCut, the most transferable idea is the data contract, not only the report interface. Raw detections, manual corrections, model semantics, and validation status should live in separate fields. A user can then tell whether a conclusion came from pixel evidence, a human decision, or a model inference.

## Conclusion

reelbench-skills matters because it makes AI shot analysis harder to bluff, not because it makes an AI “understand cinema” in one command.

FFmpeg owns measurable facts. The model owns fields that require visual interpretation. Code checks timeline closure, enums, evidence, and asset completeness. The result becomes both an interactive report and a synchronized review video. That boundary is more production-ready than one impressive multimodal answer because its artifacts can be inspected and its failures can be located.

It is not an automatic editor or a judge of film quality. A better name for what it provides is a **shot-analysis evidence chain**: video to cuts, cuts to semantics, semantics to deterministic validation, and structured data back to a playable review artifact.
