## 一句话总结

Anthropic 用 GAN 启发的"生成器 + 评估器"多 Agent 架构，让 Claude 在前端设计和长时间自主编程两个方向上突破了单 Agent 的天花板——一句话 prompt 就能产出功能完整的全栈应用。

---

## 背景：为什么单 Agent 不够用

Anthropic 团队之前已经做过 [long-running coding agent harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) 的实验，用初始化 Agent 拆任务 + coding Agent 逐 feature 实现的方式。社区里也有类似的 "Ralph Wiggum" 方法（用 hooks 让 Agent 持续迭代）。

但两个核心问题一直没解决：

### 1. Context 焦虑（Context Anxiety）

模型在长任务中 context window 越填越满，会开始"草草收尾"——它觉得自己快到上限了，就赶紧结束工作。Sonnet 4.5 上这个问题尤其严重，compaction（摘要压缩）不够，必须做 context reset（完全清空上下文 + 结构化交接）。

### 2. 自评偏高（Self-Evaluation Bias）

让 Agent 评价自己的作品？它会自信地夸赞——即使人类一眼就看出质量平庸。这在前端设计这种主观领域尤其明显，没有类似"测试通过/失败"的硬标准。

**核心洞察：让做事的 Agent 和评判的 Agent 分开，比让一个 Agent 自我批判要有效得多。**

## 前端设计：把"好不好看"变成可打分的标准

Claude 默认生成的前端设计是"能用但无聊"——安全、可预测、没有审美风险。

### 四个评分维度

团队定义了四个评分标准，同时给 generator 和 evaluator 看：

| 维度 | 说明 | 权重 |
|------|------|------|
| **设计质量** | 整体是否协调统一，有没有独特的 mood 和 identity | **高** |
| **原创性** | 有没有定制的设计决策？还是模板 + 库默认 + "AI slop"？ | **高** |
| **工艺** | 排版层级、间距一致性、色彩和谐度 | 低（默认就不错） |
| **功能性** | 用户能不能理解和使用 | 低（默认就不错） |

重点惩罚"紫色渐变 + 白卡片"这种典型 AI slop 模式。

### 迭代循环

- 基于 [Claude Agent SDK](https://platform.claude.com/docs/en/agent-sdk/overview) 编排
- Generator 生成 HTML/CSS/JS
- Evaluator 用 **Playwright MCP** 实际操作页面（不是看截图），打分 + 写详细批评
- 反馈回 Generator 进行下一轮迭代
- 每次 5-15 轮迭代，单次运行最长 4 小时

### 惊人的创意跳跃

一个荷兰艺术博物馆网站的例子：前 9 轮都是常规暗色主题 landing page。第 10 轮，模型**完全推翻方案**，重新设计成一个 3D 空间体验——CSS 透视渲染的棋盘地板、墙上自由挂放的画作、用"门"导航不同展厅。这种创意跳跃在单次生成中从未出现过。

## 全栈编程：三 Agent 架构

把 GAN 模式扩展到完整软件开发：

```
用户 1-4 句话 prompt
       ↓
   [Planner Agent]
   把简短 prompt 扩展成完整产品 spec
   注入 AI 功能机会
       ↓
   [Generator Agent]
   按 sprint 逐 feature 实现
   React + Vite + FastAPI + SQLite
   每轮 sprint 结束自评
       ↓
   [Evaluator Agent]  
   用 Playwright MCP 像用户一样点击测试
   按标准打分，低于阈值就 fail
   反馈给 Generator 修复
```

### Sprint Contract 机制

每个 sprint 开始前，Generator 和 Evaluator **先谈好"完成标准"**——Sprint 3 的 Level Editor 就有 27 条测试标准。这避免了 spec 太高层和实现脱节的问题。

### 实战对比：2D 复古游戏制作器

| 方式 | 时间 | 成本 | 结果 |
|------|------|------|------|
| Solo Agent | 20 分钟 | $9 | 布局浪费空间，游戏核心功能坏了 |
| 完整 Harness | 6 小时 | $200 | 16 个 feature，游戏能玩，有 AI 集成 |

Solo 版的游戏**根本跑不起来**——实体出现了但不响应输入，代码里的 wiring 断了。Harness 版虽有小瑕疵（角色跳到平台会重叠），但核心功能完整。

### Evaluator 抓到的真实 Bug 例子

- 矩形填充工具只在起点和终点放 tile，不填中间区域
- 删除实体的快捷键逻辑条件写错了
- API 路由顺序问题导致 FastAPI 把 `reorder` 当成整数 ID 解析

**关键教训：Claude 默认是糟糕的 QA Agent。** 它会发现问题然后说服自己"没那么严重"就放过了。需要多轮 prompt 调优才能让 Evaluator 真正严格。

## 迭代简化：Opus 4.6 的飞跃

### 原则

> 每个 harness 组件都编码了"模型做不到这件事"的假设。这些假设值得压力测试——因为它们可能一开始就是错的，或者随着模型进步而过时。

### Opus 4.6 带来的变化

- **去掉 sprint 分解** — Opus 4.6 能连续编码 2+ 小时不跑偏
- **去掉 context reset** — Opus 4.6 不再有 context anxiety
- **Evaluator 变成可选** — 模型能力边界外移，简单任务不再需要评估器

### DAW（数字音频工作站）实战

一句话 prompt → 4 小时 → $124 → 浏览器端功能完整的音乐制作程序

| 阶段 | 时间 | 成本 |
|------|------|------|
| Planner | 4.7 min | $0.46 |
| Build 第 1 轮 | 2h 7min | $71.08 |
| QA 第 1 轮 | 8.8 min | $3.24 |
| Build 第 2 轮 | 1h 2min | $36.89 |
| QA 第 2 轮 | 6.8 min | $3.09 |
| Build 第 3 轮 | 10.9 min | $5.88 |
| QA 第 3 轮 | 9.6 min | $4.06 |
| **总计** | **3h 50min** | **$124.70** |

QA Agent 仍然抓到了核心问题："clips 不能在 timeline 上拖动，没有合成器旋钮和鼓垫 UI，没有 EQ 曲线可视化——这些不是边缘功能，是 DAW 的核心交互。"

## 对 Builder 的实用启示

### 1. 分离生成和评估

不要让 Agent 自评。用独立的评估 Agent + 具体评分标准。调优评估器比让生成器自我批判容易得多。

### 2. 每代模型都重新审视你的 harness

> "有趣的 harness 组合空间不会随着模型进步而缩小——它会移动。"

Opus 4.5 需要 sprint 分解 + context reset。Opus 4.6 都不需要了。你的 harness 中哪些组件还在承重？

### 3. 把主观判断变成可打分的标准

"设计好不好？"很难回答。"是否符合这些设计原则？"就可以打分了。这个思路适用于所有主观质量评估。

### 4. Evaluator 要实际操作，不是看截图

用 Playwright MCP 让评估 Agent 真正点击、导航、测试——像真实用户一样。静态评估远不如交互式评估有效。

### 5. Agent 间通信用文件

Anthropic 的方案很朴素——Agent 之间通过读写文件交流。一个写文件，另一个读取并在文件中回应。简单、可追溯、好调试。

## 总结

这篇博文是 Anthropic 在 harness engineering 领域最详细的一篇实战记录。核心信息很清晰：

- 单 Agent 有天花板，多 Agent 架构能突破
- GAN 式"生成 + 评估"循环是一个通用模式
- 模型每次升级，harness 都值得重新精简
- 真正的工程价值在于找到下一个有趣的 harness 组合

如果你在做长时间 Agent 编程任务，这篇文章里的 pattern 值得直接抄。
