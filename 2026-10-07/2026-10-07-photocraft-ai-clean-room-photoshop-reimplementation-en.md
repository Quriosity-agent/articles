# PhotoCraft Source Audit: The 244K-Line Rust Editor Is Real; Claims of “Decompiled Photoshop” and “Adobe Nuked” Are Unsupported

> **Bottom line:** PhotoCraft is a real, downloadable native Rust image editor moving at extraordinary speed. It is also early alpha. Its own roadmap puts genuine Photoshop parity below 50%, while Eric S. Raymond's claim that Photoshop was decompiled, converted into a specification, and regenerated by an LLM has no public evidence behind it.

![PhotoCraft's main interface with layers, curves, and type](imgs/photocraft-ai-clean-room-photoshop-reimplementation/photocraft-demo.jpg)

On October 7, 2026, Eric S. Raymond described [PhotoCraft](https://github.com/storytold/photocraft) on X as the doom he had predicted for Photoshop: an open-source clean-room reimplementation. He then guessed at a specific production pipeline: decompile Photoshop into source, translate that source into a non-code specification, and ask an LLM to generate Rust. From there came the verdicts “Adobe just got nuked” and “closed source is dead.”

The post identifies a real shift, but collapses three separate questions into one story:

1. **Is PhotoCraft real software?** Yes.
2. **Was AI used extensively to build it?** The creator's statements, commit history, and velocity support that conclusion.
3. **Was it generated from a decompilation of Photoshop?** There is no public evidence for that claim, and it conflicts with the repository's stated clean-room rules.

The useful question is therefore not whether Photoshop died overnight. It is how far AI has compressed the cost of establishing the surface area of a large desktop application, and why the hardest remaining work is still not measured in lines of code.

---

## 01 | Not Vaporware, Not a Photoshop Replacement

At the repository commit inspected on October 7, 2026, `4337a6227a823a28728e68aed844feab62b3314d`, PhotoCraft had the shape of a substantial software project:

- approximately **244,000 lines of Rust** across 1,000 tracked files;
- 33 `Cargo.toml` files and more than twenty internal workspace crates;
- roughly **2,826 Rust test annotations**;
- 303 commits with multiple outside contributors;
- targets for macOS, Windows, Linux, FreeBSD, and WebAssembly;
- a [v0.2.0 release](https://github.com/storytold/photocraft/releases/tag/v0.2.0) containing DMGs, Windows installers, AppImage, deb, rpm, ARM64 packages, a CLI, a web bundle, and checksums;
- passing Windows, macOS, Ubuntu, corpus, WASM, and ARM64 jobs in the GitHub Actions snapshot inspected.

I also ran `cargo metadata --no-deps` against the source checkout; the workspace manifests resolved successfully. That is enough to rule out a README-only project decorated with concept screenshots.

It is not enough to establish Photoshop parity. PhotoCraft's own [roadmap](https://github.com/storytold/photocraft/blob/main/docs/roadmap.md) says that wired menus do not prove behavior or fidelity, that real parity is “well below 50%,” and that readiness for a professional to switch for daily work is roughly 25%–35%.

**This audit verified source structure, Git history, release artifacts, CI records, and project documentation. It did not perform a full local build, launch, or Photoshop-controlled rendering trial.** The screenshots and compatibility measurements below are therefore project evidence, not an independent product acceptance test.

## 02 | Eight Days: From `one-shot` to 244K Lines

The repository was created on September 30. Its first commit contained only a README and `.gitignore`; the next major commit, named [`one-shot`](https://github.com/storytold/photocraft/commit/16941f7), added about 42,000 lines at once. By October 7, the repository contained roughly 244,000 lines of Rust. Commit volume was distributed as follows:

| Date | Commits |
|---|---:|
| Sep 30 | 6 |
| Oct 1 | 15 |
| Oct 2 | 24 |
| Oct 3 | 26 |
| Oct 4 | 59 |
| Oct 5 | 102 |
| Oct 6 | 45 |
| Oct 7 | 26 |

Creator Brandon Thomas wrote in a [public post](https://www.reddit.com/r/Bard/comments/1wxmqpt/ive_created_open_source_100_rust_cleanroom/) that he used Claude Opus 5.5 to help recreate seven Adobe-class applications. That statement, the `one-shot` commit, and the iteration rate support the conclusion that AI contributed heavily.

They do not establish that Photoshop was decompiled. An LLM can generate large implementations from public format specifications, behavioral tests, prior product experience, and architectural constraints supplied by a developer. **AI assistance, a clean-room claim, and a decompiled source are three different chains of evidence.**

## 03 | What Was Actually Implemented

PhotoCraft is not simply a Photoshop-styled web interface. It is a native Rust editor with:

- an `egui/eframe` desktop UI;
- a document model for layers, masks, adjustments, type, vectors, and history;
- a CPU compositor as a reference path and a `wgpu` GPU compositor;
- 256×256 sparse tiles and copy-on-write behavior for large canvases;
- separate IO paths for PSD, common raster formats, and native `.pcraft` documents;
- a shared command registry serving the desktop UI, CLI, JSON control, and MCP;
- a WebAssembly build of the core application.

The most consequential choice is not Rust by itself. It is the **everything-is-a-command** architecture. A menu click, CLI invocation, JSON request, or agent tool eventually enters the same command system. Automation is therefore not a macro layer bolted onto a completed GUI; it shares semantics with the editor's own operations.

PhotoCraft may ultimately be more interesting as an editor designed from day one for joint human and agent operation than as another Photoshop clone.

## 04 | PSD Compatibility: Round-Trip Is Not Visual Parity

The project README reports encouraging PSD figures: after passing through the application model, re-saved files preserve rendering for 307 of 309 `psd-tools` files and 169 of 170 files in a mixed corpus. The standalone parser/writer also achieves byte-identical round trips for parseable corpus files.

Those are useful engineering measurements, but they represent different levels of evidence:

| Level | What it establishes | What it does not establish |
|---|---|---|
| Parseable | The file can be read | It looks like Photoshop |
| Round-trip | The saved file can be read again, with structure or bytes preserved | Every effect, font, and color is identical |
| Photoshop oracle / visual comparison | Pixels or behavior were compared against Photoshop | Every production document is covered |

PhotoCraft's [scorecard](https://github.com/storytold/photocraft/blob/main/docs/scorecard.md) correctly separates parser round-trip, application-model round-trip, and Photoshop-oracle results. That distinction matters because PSD is broad, old, and full of edge cases. “The file survived” is only the first milestone.

## 05 | The Project Is More Sober Than the Viral Post

The October 5 roadmap identifies gaps that include:

- around twenty missing Photoshop tools;
- effectively no generative-AI feature set;
- no ExtendScript, UXP, `.atn`, Adobe Libraries, or cloud-document compatibility;
- no Photoshop `.8BF` plugin support, with a separate WASM plugin system instead;
- incomplete typography, professional-workflow depth, and large-document performance;
- 60 of 133 settings that currently have no effect.

More revealingly, 626 of 626 menu entries can dispatch while the scorecard still records a badly over-budget 24 MP Content-Aware Scale test and a GPU-compositor crash during a 150-layer nudge. **A clickable menu measures surface coverage, not completion. Existing code is implementation evidence, not quality evidence.**

This is why 244,000 lines and 25%–35% daily professional switch-readiness can both be true. AI first compresses the cost of filling out the product surface. Edge cases, format semantics, visual fidelity, performance work, and maintenance remain expensive.

## 06 | What “Clean Room” Does and Does Not Mean

PhotoCraft currently says it was implemented from public Adobe PSD documentation, ICC and ISO standards, research papers, and observed behavior, without proprietary Adobe code, shaders, or assets. Its workspace is licensed `MIT OR Apache-2.0`, and most crates forbid `unsafe` code.

Clean-room development, however, is a process and provenance boundary, not an automatic legal certification created by a README label. The repository history also contains a relevant nuance. Early versions of `AGENTS.md` and the architecture document explicitly said the team had studied the behavior and architecture of another proprietary editor, Photon Studio; warned contributors not to paste code from its readable bundle; and treated its menu snapshot as a feature backlog. Commit [`9c9a680`](https://github.com/storytold/photocraft/commit/9c9a680) removed those named references on October 2, while current documentation uses the broader phrase “Photoshop and other proprietary editors.”

That history **does not prove copying, and it does not prove the clean-room claim false**. It shows that the behavioral reference story was more specific than today's homepage summary. Whether the entire process meets a legal clean-room standard would require an independent audit.

Raymond's proposed “decompile Photoshop → write a specification → generate Rust” pipeline is likewise only a guess. The public repository does not demonstrate such a pipeline; its documented rules say not to copy proprietary code. Reporting the guess as fact would be unwarranted.

## 07 | Seven Repositories Are Not “the Entire Adobe Suite”

The `storytold` account does host PhotoCraft, FilmCraft, VectorCraft, EffectCraft, DesignCraft, PrintCraft, and LightCraft, aimed respectively at Photoshop-, Premiere-, Illustrator-, After Effects-, InDesign-, Acrobat-, and Lightroom-like workflows.

This is more than a screenshot campaign. The creator is trying to apply shared Rust infrastructure, command systems, and AI-assisted development across a family of creative tools. But seven repositories existing is not the same as seven mature applications, much less the entire Adobe suite. These projects are broadly early alpha. Repository count measures ambition and surface area, not production replacement.

## 08 | What Adobe Should Actually Notice

“Adobe got nuked” is premature, but PhotoCraft still exposes three important changes.

### 1. The cost of starting a software clone is collapsing

Until recently, one person could not plausibly establish cross-platform desktop UI, a document model, GPU compositing, PSD IO, CLI and MCP control, installers, and thousands of test entry points in eight days. AI did not bring each component to professional quality, but it compressed the construction of a complete skeleton from a team-scale project into an individual-scale experiment.

### 2. Competition moves from feature lists to verification systems

When AI can fill menus and commands quickly, durable value moves toward corpora, oracles, compatibility tests, performance baselines, user evidence, plugin ecosystems, and maintenance. PhotoCraft's most credible asset is not its 626 menus. It is the project's willingness to publish failures and low maturity estimates in its scorecard.

### 3. Agent-native editors become a distinct product direction

Traditional applications wrap automation around a UI. PhotoCraft treats one command registry as the substrate for UI, CLI, JSON, and MCP. Even if it cannot replace Photoshop soon, that architecture may create different advantages in batch work, reproducible edits, and agent collaboration.

Its MCP documentation includes read/write-root restrictions and bearer-token protection for a local bridge, but the project also notes that fine-grained session and tool-capability permissions are not yet present. That makes it suitable for controlled local experiments, not direct exposure to an untrusted broker.

## 09 | Who Should Use It Today

PhotoCraft currently makes sense for:

- developers studying Rust desktop graphics, PSD parsing, or GPU compositing;
- contributors willing to report edge cases in an early alpha;
- experimental CLI, JSON, or MCP workflows where outputs will be reviewed;
- anyone studying how AI changes the organization of large software projects.

It is not yet a straightforward replacement for:

- commercial production that depends on complex PSDs, precise typography, and color management;
- teams dependent on Photoshop plugins, Actions, UXP, Adobe Fonts, or Libraries;
- delivery workflows that cannot tolerate rendering differences, performance regressions, or round-trip risk.

A sensible trial would use copies of representative documents and a fixed acceptance suite: visual comparison, type, blend modes, smart objects, masks, color profiles, save/reopen behavior, cross-application reopening, and large-file performance.

## 10 | The Meaning of “First Version” Has Changed

The most persuasive PhotoCraft fact is not Raymond's speculation. It is the repository itself: one developer, assisted by AI, built a downloadable, testable, cross-platform Rust application with a genuine editing engine in a remarkably short time, then attracted outside contributors.

The repository supplies the other half of the answer too. Two hundred forty-four thousand lines, 626 menus, and seven projects did not automatically become a professional workflow. The project's own 25%–35% switch-readiness estimate is closer to reality than “Adobe got nuked.”

A more defensible conclusion is this: **closed-source software did not die because one repository appeared, but proprietary vendors can no longer assume that reproducing their visible feature surface necessarily requires a large team and many years.** AI is making the first version abundant. Compatibility, sustained maintenance, ecosystem depth, and user trust become scarcer and more valuable.
