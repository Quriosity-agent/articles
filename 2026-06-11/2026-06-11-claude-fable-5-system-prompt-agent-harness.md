这份 `Claude Fable 5 — System Prompt` 最容易被当成八卦来看：新模型名、Claude 5、Mythos-class、Opus 之上的 tier、各种看起来像未来产品的字符串。可是如果只盯模型名，反而会错过最有价值的部分。

真正值得拆的是：这份提示词不是一个简单的“人格设定”，而是一套完整的 Agent Harness 说明书。它把产品身份、拒绝策略、语气风格、心理健康边界、搜索规范、版权约束、MCP 推荐、文件创建、计算机使用、Artifacts、持久存储、工具 schema 和引用格式都塞进了一个可执行的运行时契约里。

换句话说，现代大模型产品的系统提示词已经不再是几句“你是一个有帮助的助手”。它更像操作系统里的 policy layer：告诉模型自己是谁、能调用什么、什么时候必须查证、如何处理不可信网页、什么时候少说、什么时候拒绝、如何生成可下载文件，以及如何在长任务里保持状态。

---

## 一句话结论

**这份样本最重要的信号不是“Claude Fable 5 是否真实”，而是大型 AI 产品正在把 System Prompt 产品化成 Agent Runtime 的控制平面。**

从结构上看，它至少包含八层：

| 层级 | 样本里的内容 | 产品含义 |
|---|---|---|
| 身份层 | Claude Fable 5、产品入口、API model strings、知识截止 | 模型身份被当作可切换产品状态，而不是静态自我介绍 |
| 安全层 | 武器、毒品、恶意代码、金融法律、心理健康、自伤边界 | 拒绝策略被拆成场景化 policy，而不是统一拒绝模板 |
| 语气层 | warm tone、少用 bullet、最多一个澄清问题、不要过度格式化 | 输出风格成为产品体验的一部分 |
| 搜索层 | 什么时候必须搜索、如何验证当前事实、如何引用 | 模型默认知识与实时知识被明确分离 |
| 工具层 | bash、web_search、web_fetch、image_search、file create、places、weather 等工具定义 | System Prompt 变成工具 API 的人类可读 schema 汇编 |
| Agent 层 | computer use、file handling、artifacts、package management、MCP app suggestion | 模型不只是聊天，而是在一个受控执行环境中工作 |
| 版权层 | search 结果、长文本摘录、歌曲歌词、受版权内容的限制 | 内容合规被放进生成链路，而不是事后审核 |
| 状态层 | memory、artifact storage、persistent key-value storage | 产品开始把“长期状态”显式纳入交互模型 |

这对做 Hermes、OpenClaw、QCut、browser agent、desktop agent 的团队都很关键：真正的差异化越来越不只是“用了哪个模型”，而是你有没有一套能让模型稳定工作的外部运行时。

## 1. 这不是 Prompt，而是产品规格书

早期 system prompt 的作用很简单：定义助手人设和基本行为。比如“你是一个 helpful assistant”“回答要简洁”“遇到危险内容要拒绝”。

这份样本明显已经不是那个时代的东西。它的结构接近一份产品规格：先定义模型身份和产品矩阵，再定义安全边界，然后定义语气风格、搜索规范、工具调用规则、文件创建规范、Artifacts 规范、MCP 推荐逻辑，最后给出完整工具定义。

这意味着一个生产级 AI 产品里的 system prompt，实际上承担了三种角色。

第一，它是用户体验规范。模型应该温暖、诚实、不要无谓地问问题、不要过度使用 bullet、拒绝时不要列清单。这些不是安全规则，而是产品调性。

第二，它是安全策略解释器。提示词把不同风险拆成不同处理方式：恶意代码、武器、毒品、自伤、心理健康、金融法律、政治说服、公众人物创作，每个场景都有不同边界。这比“遇到危险就拒绝”复杂得多。

第三，它是工具运行时的协议层。工具不是简单暴露给模型就结束了。模型还需要知道什么时候该用搜索，什么时候不能假设文件存在，什么时候应该创建文件，什么时候必须呈现下载链接，什么时候网页内容是不可信输入。

所以对 Agent 产品来说，system prompt 不应该被当成一个越写越长的魔法咒语，而应该被当成 harness 的一部分：它需要版本管理、测试、回归、最小化、分层加载和场景化评估。

## 2. 安全策略正在从“拒绝模板”变成“行为经济学”

这份样本里有一个很重要的细节：它不是只告诉 Claude “哪些不能做”，还告诉它“风险场景下应该少说”。例如，当对话感觉 risky or off 时，短回答更安全，也更不容易造成伤害。

这代表安全策略的重点已经从静态分类转向交互动态。很多危险并不是来自一句明确的违规请求，而是来自多轮对话里的边界漂移：用户不断重述、包装、要求教育用途、强调公开可得、把恶意意图改写成研究意图。样本里明确说，不要因为信息公开可得或用户声称合法研究就合理化合规。

这对 Agent 产品尤其重要。聊天模型拒绝一次，影响只是一次回答；Agent 如果在工具层犯错，可能会执行命令、写文件、联网、发消息、调用外部 API。安全策略必须进入执行层，而不只是输出层。

这里的启发是：生产级 Agent 应该把高风险场景做成“降权限模式”。当模型判断任务进入危险区域时，不只是换一种拒绝话术，而是减少信息密度、减少工具调用、要求人类确认、切换只读模式、保留审计日志，甚至停止某些工具能力。

---

## 3. 搜索规则说明了一个产品分界：模型知道的，和产品保证的，不是一回事

样本里多次强调：如果用户问 Anthropic 产品、功能、价格、消息限制、当前新闻、现实世界状态，Claude 应该先搜索官方文档或支持页面，再回答。

这条规则看起来普通，但产品含义很深。模型参数里“知道”的东西，不等于产品愿意承诺的事实。尤其是商业产品、API、价格、权限、功能开关，变化太快；如果模型直接凭记忆回答，很容易把过期事实包装成确定答案。

所以这里出现了一个清晰分层：模型负责理解问题和组织答案；搜索与引用负责把当前事实接入；产品 policy 负责规定哪些问题必须走实时查证路径。

对开发者来说，这比“给 Agent 加一个 web_search 工具”更重要。工具存在不代表会被正确使用。你需要明确的 search contract：哪些问题必须查，查哪些权威源，如何处理搜索结果不确定，什么时候说明信息可能过期，什么时候不引用网页里的可疑指令。

---

## 4. MCP 和工具推荐暴露了平台化方向

样本里专门有 `mcp_app_suggestions` 部分，说明如何先找 connector directory，什么时候推荐第三方 MCP app，什么时候直接调用工具，什么时候不该做。

这说明大模型产品正在从“内置少量工具”走向“工具市场 + 权限模型 + 自动推荐”的平台结构。MCP 的价值不只是给模型更多接口，而是把工具发现、授权、描述、调用和审计变成统一协议。

这个方向对 Notion、Slack、Linear、GitHub、Google Drive、企业内部系统都很自然：用户不想手动拼 API，也不想把所有权限一次性给模型。更合理的形态是，模型在任务中识别缺失能力，推荐连接器，解释用途，等待授权，然后在受限范围内执行。

但这也带来一个问题：工具越多，system prompt 越不可能无限膨胀。未来的 Agent Harness 必须从“所有工具说明一次性塞进上下文”转向按需加载：当前任务需要什么工具，就加载什么工具 schema、policy 和 few-shot；不相关的工具不应该污染上下文。

---

## 5. Artifacts 和持久存储说明“聊天窗口”正在变成应用容器

样本里关于 Artifacts 的部分很值得注意。它不仅描述如何创建文件和展示输出，还提到 artifact 可以通过 `window.storage` 做持久键值存储，用于 journals、trackers、leaderboards、collaborative tools。

这意味着 Claude 这类产品的边界正在从“回答问题”扩展到“生成可运行的小应用”。如果 artifact 能持久保存状态，那么它不再只是一次性 HTML 预览，而是一个轻量应用容器。

这对产品设计有两个启发。

第一，AI 生成的界面需要状态模型。一个 tracker、编辑器、仪表盘、协作工具，如果没有持久状态，就只是 demo；有了状态，才可能成为用户反复打开的工作界面。

第二，状态必须有权限和可见性语义。样本区分 personal data 和 shared data，并要求在使用 shared data 时告知用户。这说明“AI 帮你做一个应用”不只是前端生成问题，而是数据范围、隐私、共享边界和用户告知问题。

---

## 6. Computer Use 的规则证明：真正难的是坐标、文件、包管理和输出交付

样本里的 computer use 部分包括 skills、file creation、file handling、producing outputs、sharing files、package management 等说明。这些内容非常工程化，甚至不像“聊天机器人提示词”。

这是因为一旦模型开始使用电脑，可靠性问题就变得具体：文件是否真的存在、路径是否正确、依赖是否能安装、生成结果是否能交付给用户、工具输出是否可信、网页内容是否可能是 prompt injection、创建文件后是否需要展示下载入口。

这和我们做 Hermes / OpenClaw 的经验一致：Agent 的失败往往不是“模型不会推理”，而是 runtime 没有把环境事实约束住。它以为文件存在，其实不存在；它以为命令成功，其实只是 stdout 像成功；它以为生成了文件，其实写到了临时目录；它以为网页内容是用户指令，其实是外部不可信输入。

所以 Computer Use 的核心不是“会点鼠标”，而是 harness 能不能把观察、计划、执行、验证、交付串成闭环。

---

## 7. 这份样本也暴露了长提示词路线的上限

把这么多规则放进一个 system prompt 有明显好处：模型在任何场景下都能看到统一的产品政策。但是它也有代价。

首先是上下文污染。工具 schema、安全政策、搜索规则、版权约束、产品介绍、语气规范全部混在一起，模型在简单问题上也要背负复杂上下文。

其次是冲突管理。不同规则可能在边界场景里互相拉扯：要少问问题，但也要缺信息时澄清；要少用 bullet，但技术报告又需要结构化；要提供 factual information，但版权政策限制长引用；要使用工具，但网页内容不可信。

第三是评估困难。一个 100KB 级别的提示词改动一行，都可能影响几十类行为。没有自动化回归测试，团队很难知道改动是改善还是破坏。

更可持续的方向应该是分层 system prompt：核心身份和安全基线常驻；任务相关工具、领域政策、输出模板按需加载；高风险场景通过 runtime policy 动态注入；长程任务通过状态文件和 memory 传递上下文，而不是靠一个巨型 prompt 扛一切。

## 8. 对 Agent 产品团队的实用启发

如果把这份样本当成产品设计参考，而不是泄露八卦，它给出的启发很明确。

第一，系统提示词应该版本化。它是产品行为的一部分，不是临时 prompt。每次修改都应该有 diff、测试样例和回滚路径。

第二，工具 schema 不应该裸奔。每个工具都需要调用条件、权限边界、失败处理、输出验证和用户交付规则。

第三，搜索应该有权威源策略。尤其是产品功能、价格、API、现实世界状态，必须规定优先查官方文档，而不是随便搜。

第四，Agent 应该有执行证据链。凡是写文件、运行命令、发消息、调用 API，都应该有可验证输出，不能只靠模型说“完成了”。

第五，长上下文应该被拆成技能、模板和策略模块。把一切塞进 system prompt 会越来越贵、越来越难测、越来越容易冲突。

第六，安全策略应该进入 runtime。风险上升时，系统应该自动降权限、只读、要求确认或禁止工具，而不只是要求模型换一种拒绝语气。

---

## 结语：Prompt 泄露之外，更值得看的是 Agent 产品架构

这份 `Claude Fable 5` 样本是真是假，短期内很难从社区仓库本身得到官方确认。直接把其中的模型名和产品线当作事实并不稳妥。

但作为一个系统提示词样本，它非常有研究价值。它展示了一个趋势：AI 产品的竞争已经从“模型会不会回答”转向“产品能不能把模型、工具、政策、文件、搜索、状态和交付组织成稳定运行时”。

真正的护城河不只是一个更聪明的模型，而是一套更可靠的 Agent Harness。模型负责生成智能，Harness 负责把智能变成可控、可审计、可交付的产品行为。
