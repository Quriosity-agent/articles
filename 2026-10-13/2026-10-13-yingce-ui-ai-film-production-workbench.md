# 影策 UI 深度拆解：AI 影视工具需要的不是更多按钮，而是一张可推进的生产地图

> **结论先行：** 影策 `open-ai-canvas` 最值得研究的，不是深色无限画布，也不是它接入了多少模型，而是它尝试把“做一部片”重新组织成一套可见、可推进的界面状态：项目里有章节，章节里有镜头，镜头关联角色与场景资产，生成结果进入任务和素材系统，Agent 的操作需要审批，确认后的镜头还能继续进入 3D 预演与时间线。它的 UI 不是围绕一次 Prompt 设计，而是围绕一条会持续数天甚至数周的制作链设计。

![影策制作概览把当前任务、章节进度、资产和画布入口放进同一项目](imgs/yingce-ui-ai-film-production-workbench/project-workbench.png)

本文是[《影策 open-ai-canvas 源码审计》](2026-10-13-open-ai-canvas-ai-film-production-graph.md)的 UI 与产品工作流补篇，不重复后端、插件协议和测试数字。分析固定到用户提供 fork 的提交 [`27c8066`](https://github.com/donghaozhang/open-ai-canvas/tree/27c8066e6da9f0d4754dc0e5c40097049fe730cf)。截至 2026 年 10 月 13 日，该 fork 仍停在这一提交，上游已经领先 7 个提交；下文只描述固定快照，不把它写成上游最新版本。

---

## 01 | 制作概览先回答“片子做到哪了”

影策没有让用户一进项目就面对空白画布。制作概览先显示当前任务、章节进度、已确认资产、待处理分镜和后续动作。这个顺序非常重要：影视项目的核心问题通常不是“我能调用哪个模型”，而是“这一章现在缺什么”。

界面因此把状态分成几层：

- 项目层记录作品、画幅、默认模型和整体进度；
- 章节层记录文本、镜头数量、资产确认与分镜推进；
- 镜头层记录描述、动作、对白、景别、机位、时长和连续性；
- 生成层记录任务、版本、报价、进度、失败与结果；
- 交付层把已确认镜头送入预演或时间线。

这让“继续处理”成为一个具体动作，而不是让用户凭记忆重新找到昨天停下的位置。制作概览真正扮演的是**项目恢复界面**：它帮助创作者在中断之后重新进入上下文。

---

## 02 | 项目、章节、资产和画布形成同一条导航链

项目顶部导航使用“制作概览、剧情章节、项目画布、角色与资产、项目设置”这样的业务语言。进入画布后，项目侧栏仍可以浏览章节、预览内容，并把章节或项目资产拖入画布中央。

这套信息架构的价值是：资产并不是一张孤立图片。角色设定属于项目，章节引用角色，镜头继续引用角色版本，画布上的媒体也保留与任务和资源的关系。用户看到的是“这是谁、用于哪一章、参与哪个镜头”，而不只是一个文件名。

对长流程创作来说，这种归属感比模型选择器更重要。模型可以替换，供应商可以切换，但角色、场景和镜头必须保持身份稳定，否则每次生成都会重新丢失上下文。

---

## 03 | 画布不是空白容器，而是三层工作空间

![影策自由画布中的角色参考、媒体节点、连接和失败状态](imgs/yingce-ui-ai-film-production-workbench/production-canvas.png)

影策画布可以拆成三层：

1. **空间层**：平移、缩放、框选、拖拽、连线、层级和小地图，帮助用户整理复杂关系。
2. **工作区层**：左侧工作区面板提供节点、资产、任务和历史；项目侧栏负责章节与项目素材；顶部和底部工具条负责全局操作。
3. **业务节点层**：角色、场景、文本、故事板、图片、视频、音频、绘图、3D 预演与时间线入口都带有自己的业务状态和操作。

源码中的 `CanvasWorkspacePanel` 不是装饰抽屉。节点列表可以搜索并定位对象，资产面板负责插入素材，任务面板显示生成状态，历史面板帮助回看操作。`CanvasProjectSidebar` 则把章节预览与项目资产继续留在画布旁边。

因此，画布承担的不是“把卡片摆好看”，而是让创作者同时看见**素材、关系、任务与下一步动作**。

---

## 04 | 故事板大节点把表格变成可执行制作单

![故事板节点在同一画布中连接角色参考、镜头描述、视频和结果图](imgs/yingce-ui-ai-film-production-workbench/storyboard-workflow.png)

影策 UI 中最有辨识度的对象，是可以容纳多镜头的故事板表格。它不只展示画面描述，还可以包含镜头时长、对白、旁白、生成进度和批量操作。故事板从“给人看的规划表”变成“可以直接启动任务的制作单”。

这个设计解决了影视生成中一个常见断点：脚本、分镜描述、参考图和生成结果分别散落在文档、聊天记录和下载文件夹里。影策让它们在同一空间中互相指向：角色参考连到故事板，故事板拆出镜头任务，结果图片和视频再回到画布。

代价也很直观。大型表格节点、图片卡、视频卡和错误卡同时出现时，画布会非常密。缩小时文字不可读，放大后又失去全局关系。这个 UI 需要更强的层级折叠、按阶段过滤、节点摘要和聚焦模式，才能在真实长项目中持续保持清晰。

---

## 05 | Agent 的 UI 核心是计划、上下文和审批

影策没有把 Agent 简化成右侧问答框。`CanvasCloudAgentPanel` 同时管理会话、计划、问题、上下文用量、技能、连接器、推理模式、权限模式和审批状态；画布节点还能通过“发送到 Agent”把明确对象加入上下文。

从用户角度看，关键不是 Agent 能否写一段漂亮回答，而是三个界面问题：

- 它正在读取哪些节点、章节和资源？
- 它计划执行哪些步骤？
- 哪些画布修改或收费生成需要我确认？

影策已经为这些问题准备了上下文范围、计划条、待回答问题、审批卡、最大积分、最大生成任务数和视频秒数等控制。Agent 的能力因此被放进一个可管理的执行边界里。

这条方向是对的，但界面负担也很重。聊天、历史、设置、技能库、连接器、计划与审批都集中在 Agent 区域，新用户需要理解许多概念。更成熟的呈现方式应根据任务阶段逐步暴露复杂度：平时只显示当前目标和下一次审批，调试时才展开上下文、事件和高级限制。

---

## 06 | 任务、失败和版本没有被藏起来

生成型产品最容易制造一种错觉：按钮按下后，转圈结束就算完成。影策的界面把“生成”视为有生命周期的任务，用户可以看到排队、运行、耗时、失败、取消、重试、报价和产物版本。

截图中的错误卡并不漂亮，却揭示了一个重要设计选择：失败仍然留在生产图中。它不会悄悄消失，让用户误以为镜头从未提交；失败节点仍保留位置、输入关系和重试入口。对长流程而言，可恢复性比瞬间整洁更重要。

在镜头工作台中，用户还可以切换最新结果与历史版本，选择当前产物，并把角色、场景或音频作为明确引用加入生成。于是一次失败、一次重跑和一次选片，不再是互相覆盖的临时结果，而是镜头状态的一部分。

---

## 07 | 3D 预演和时间线让画布有了出口

如果所有节点最终只停在画布里，产品仍然只是一个整理生成结果的空间。影策继续提供两条下游路径：3D 预演与时间线。

3D 预演工作台可以处理演员、姿态、灯光、机位、视口和镜头序列，预演结果还能回写为画布节点。时间线则负责片段编排、修剪、字幕、预览与服务端导出。两者最重要的意义不是功能数量，而是让用户能够回答：“这张分镜确认之后，下一步去哪里？”

从 UI 角度看，这让画布成为生产中枢，而不是终点。角色和场景在前期建立，故事板组织镜头，预演验证空间与节奏，生成结果进入时间线，修改后又可以返回上游继续迭代。

不过固定快照中的 3D 与长片编辑仍带有明显 MVP 边界。界面已经表达完整方向，但真实复杂场景、长时间线性能、跨阶段版本回滚和商业模型调用仍需要部署环境验收。

---

## 08 | 管理后台揭示了 UI 的另一半：它也服务运营者

![影策管理端把模型、渠道、用量、成本和运营状态放在一起](imgs/yingce-ui-ai-film-production-workbench/operations-console.png)

创作端负责让作品向前推进，管理端则负责让平台能够持续运行。模型渠道、逻辑模型、价格、积分、订单、请求日志、存储、用户和功能开关都进入统一后台。

这意味着影策 UI 同时面对两类人：创作者关心镜头是否生成、角色是否一致、素材能否继续编辑；运营者关心调用走了哪个渠道、花了多少、是否失败、能否追责和对账。

两套界面共用任务、资源、模型和成本身份，是影策产品闭环的重要部分。它也解释了为什么系统显得“重”：这不是一张网页画布，而是一套需要被部署、配置、监控和升级的生产平台。

## 09 | 它的 UI 优点与当前代价

| 维度 | UI 优点 | 当前代价 |
|---|---|---|
| 项目恢复 | 制作概览直接暴露下一步 | 首页信息依赖完整项目状态 |
| 章节与资产 | 业务对象有明确归属 | 概念多，首次学习成本高 |
| 画布 | 素材、任务、关系和结果同屏 | 大节点混排后视觉密度很高 |
| 故事板 | 规划表可以直接执行生成 | 全局视野与局部编辑频繁切换 |
| Agent | 上下文、计划、技能与审批可见 | 面板功能密集，渐进披露仍不足 |
| 失败恢复 | 失败和历史版本仍可追踪 | 错误态会进一步增加画布噪声 |
| 预演与剪辑 | 生成结果有明确下游出口 | 复杂项目仍需真实环境验证 |
| 运营后台 | 渠道、成本、任务和用户可管理 | 部署和运营责任明显增加 |

影策的 UI 并不轻，也不追求第一次打开就像消费级应用一样简单。它选择先表达生产关系，再逐步解决复杂度。这个选择适合有章节、角色连续性、镜头版本和多人分工需求的团队；对于只想偶尔生成一张图的人，整套项目结构可能显得过重。

---

## 10 | 最终判断

影策真正有价值的 UI 命题是：**AI 影视创作不能只记录 Prompt，还要记录作品状态。**

一部片不会因为某次生成成功就完成。角色要跨镜头保持身份，章节要拆成镜头，镜头要经历草稿、参考、生成、失败、重试、选片、预演和剪辑。影策把这些状态尽量变成可见对象，并让项目、画布、Agent、任务、资产和下游编辑共享它们。

它当前最需要继续打磨的，不是再增加入口，而是降低同屏密度、强化阶段聚焦、简化 Agent 的渐进交互，并让跨章节、跨镜头和跨下游工具的状态变化更容易理解。

所以最准确的产品描述不是“开源 AI 无限画布”，而是：**一套试图把 AI 影视制作从零散生成，变成可恢复、可审批、可追踪生产流程的视觉工作台。**
