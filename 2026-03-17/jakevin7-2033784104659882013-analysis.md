## 一句话总结

**Harness Engineering 不是优化模型，而是优化模型运行的"环境"。** 工程师从"代码编写者"变成"环境建筑师"。

---

## 什么是 Harness Engineering？

2025-2026 年 AI 工程领域最重要的新概念。不是工具、不是框架，而是一套围绕 AI Agent 构建的**约束、反馈与控制系统**——让 Agent 在人类设定的边界内自主、可靠、可持续地工作。

三代范式的演进：

| 阶段 | 核心 | 交互模式 |
|------|------|---------|
| Prompt Engineering | 写好提示词 | 你问我答 |
| Context Engineering | 管好上下文 | 你问我答（带记忆） |
| **Harness Engineering** | **设计约束系统** | **赛道设计** |

质变在于：人不再干预 AI 的每一步操作，而是构建一整套系统来约束、引导和验证 Agent 的自主行为。

## 为什么需要 Harness？

### Agent 的"翻车"规律

Anthropic 的 Justin Young 发现：给 Agent 一个复杂项目，它的第一反应是试图在一个会话里全部做完。结果：

- context window 耗尽，留下半成品代码
- 没有任何记录，下一个 Agent 会话不知道前一次做了什么
- 过早宣布完成，大量功能未经验证

**这不是某个模型的问题，而是所有 Agent 的结构性缺陷。**

### "信任债务"概念

Cassie Kozyrkov 提出的核心洞察：

> AI 就像一个极其听话但缺乏背景知识的实习生。它倾向于填补你指令中的空白，进行"自信的即兴发挥"。如果你不审计它的假设，这些假设就会变成"信任债务"——目前看起来没问题，但在未来某个时刻会爆炸。

信任债务的三个特征：**不可见、累积、爆发**。

### 范式错位

我们已经进入"AI 写代码"的时代，但工程体系还停在"人写代码"的范式里。Agent 一天生成几百个 PR 时，人工 Code Review、靠人记架构规范、手动文档更新——全部崩塌。

## OpenAI 百万行代码实验

Ryan Lopopolo 披露的 5 个月内部实验核心发现：

**工程师不写代码之后，80% 的时间花在了构建 Harness 上。**

核心理念八个字：**人类掌舵，智能体执行。**

> 当 Agent 遇到困难时，工程师的思考不是"我该怎么帮它写完这段代码"，而是："Agent 缺乏什么能力？需要什么工具、什么抽象层、什么结构？"

### Harness 三大组件（Böckeler 归纳）

**1. Context Engineering（上下文工程）**
- 代码库中持续增强的知识库
- "地图式"渐进信息披露，不是全知百科全书

**2. Architectural Constraints（架构约束）**
- 确定性 linter + 结构化测试强制执行
- 层级依赖模型：Types → Config → Repo → Service → Runtime → UI
- 违规代码在 CI 中直接被拒绝

**3. "Garbage Collection"（垃圾回收）**
- 后台定期运行清理 Agent
- 扫描文档-代码不一致、架构违规
- 对抗熵增和代码腐烂

### Böckeler 的批判

值得注意：Böckeler 指出 OpenAI 文章**缺少功能和行为的验证**讨论，并提醒"OpenAI 在让我们相信 AI 可维护代码方面有既得利益"。

## Anthropic 的长跑方案

Justin Young 解决的底层问题：Agent 怎么跨越 context window 限制，实现长期运行？

### 三个精妙设计

**全标失败策略：** 所有功能初始标记为"失败"，Agent 只能通过修改状态来标完成，不能删除测试用例。堵死了 Agent 通过"降低标准"来"完成"任务的路。

**每次只做一件事：** 强制"做一个功能就停"看起来效率低，但总体完成率高得多。一块一块吃蛋糕，每块吃完，好过一口气吃半途而废。

**进度文件作跨会话记忆：** `claude-progress.txt` 是 Agent 的外部记忆。每个新会话先读进度文件 + git log，从断点继续。

## LangChain 的定量验证

最有说服力的数据：**同一个模型，仅改变 Harness，排名从 30+ 跃升至 Top 5。**

### 四个关键改动

**1. Plan-Build-Verify-Fix 强制闭环**
Agent 宣告完成前强制拦截，必须跑验证。四步：规划 → 构建 → 验证 → 修复。

**2. 环境上下文注入**
Agent 启动时注入目录结构、可用工具、超时时间、测评标准。

> LangChain 的定义：Harness 工程师的职责是——准备和投递上下文，使 Agent 能够自主完成工作。

**3. 死循环检测**
跟踪文件编辑次数，超过 N 次注入提示"考虑重新审视方案"。

**4. 推理三明治策略**
不是"推理越多越好"。规划阶段用 xhigh，执行阶段降到 high，验证阶段回到 xhigh。在正确的阶段投入正确量级的推理。

## Cassie Kozyrkov 的 12 条法则（核心摘要）

1. **人类掌舵，Agent 执行**
2. **可读性优先（Legibility）**——Agent 行为必须对人类可追溯
3. **明确边界**——越清晰的规矩 → 越大的自主权
4. **全面文档化**——不只给人看，更给下一个 Agent 看
5. **管理吞吐量**——几百个 PR 时必须有自动化审查
6. **持续清理**——对抗代码库熵增
7. **知道何时升级**——哪些决策必须由人类做

核心态度：即使 Agent 表现优秀，也要像它是"最粗心的员工"一样建立安全网。

## Harness 五大核心组件

综合六篇文献的归纳：

**1. 结构化知识系统** — AGENTS.md 当地图，不当百科全书。context window 是稀缺资源。

**2. 机械化架构约束** — 把"品味"编码成机器可执行的检查。Linter 错误信息本身就是教学材料。

> 为了获得更高的 AI 自主性，运行时必须受到更严格的约束。增加信任需要的不是更多自由，而是更多限制。

**3. 可观测性注入** — 观测不再只给人看，而是给 AI 看。截图验证、日志查询、浏览器操作。

**4. 自修复闭环** — 后台清洁 Agent 定期扫描，自动提交重构 PR → CI 验证 → 自动合并。小额、高频、持续偿还技术债务。

**5. Agent 互审机制** — Agent A 写代码，Agent B 审代码。人类只介入架构层面的重大决策。

## 核心洞察：约束换自主

**规矩越明确 → Agent 独立做的事越多。约束越严格 → 信任越高 → 自主权越大。**

和人类社会一致：
- 法律越完善的社会，个人自由度越高
- 高速公路有护栏，你才敢踩到 120 码
- 手术室无菌规程越严格，手术越安全

### 工程师的重新定义

| 传统 | Harness 时代 |
|------|------------|
| 价值 = 写代码的速度和质量 | 价值 = 设计系统的能力 |
| 核心技能 = 编码 | 核心技能 = 约束设计、反馈回路、控制系统 |
| 产出 = 代码 | 产出 = Agent 可靠运行的环境 |

## 三句话理解 Harness Engineering

1. **解决的不是"怎么让 AI 更聪明"，而是"怎么让 AI 可控地持续工作"。**
2. **核心逻辑是"用约束换自主"。** 规矩越明确，Agent 能独立做的事越多。
3. **正在重新定义"工程师"。** 你的价值不取决于写代码的速度，而取决于设计约束、反馈回路和控制系统的能力。

> AI 已经是千里马。千里马没缰绳，跑得再快也到不了目的地。Harness Engineering，就是这个时代最重要的缰绳。
